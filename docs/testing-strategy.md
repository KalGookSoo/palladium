# palladium 테스트 전략

moov 프로젝트에서는 "집계·계산 로직을 View 안에 그대로 두면 나중에 View를 인스턴스화하지 않고는 테스트할 수 없다"는 문제를 구현 이후에야 발견해 되돌아가 리팩터링했다. tempo 프로젝트는 이 문서의 원칙을 구현 시작 시점부터 지켜 같은 실수를 반복하지 않았다. palladium도 코드가 없는 지금 시점부터 같은 원칙을 먼저 세운다.

## 현재 상태

- Xcode 프로젝트만 생성된 상태이고, 아직 기능 코드는 없다.
- `palladiumTests/palladiumTests.swift`는 Xcode 템플릿 스캐폴딩 그대로 **Swift Testing**(`import Testing`, `@Test`)으로 남아있다 — 그대로 유지한다.
- `palladiumUITests/palladiumUITests.swift`는 Xcode 템플릿 스캐폴딩 그대로 **XCTest**로 남아있다 — 그대로 유지한다.

## 원칙: 편집/타임라인 계산 로직은 View 밖의 순수 타입으로 분리한다

영상 편집 앱의 핵심은 "클립과 타임라인의 상태"이지 화면이 아니다. 클립 트림/순서 계산, 타임라인 합성, 자막 타이밍 계산, 내보내기 설정 검증을 View의 `@State`나 UI 이벤트 핸들러 안에 직접 넣지 않는다. `AVFoundation`(`AVPlayer`, `AVMutableComposition` 등) 같은 실제 미디어 프레임워크는 얇은 어댑터로만 쓰고, "지금 타임라인이 어떤 상태인가"는 View나 미디어 프레임워크 타입에 의존하지 않는 순수 struct/함수로 계산한다.

## 유닛 테스트 (`palladiumTests`, Swift Testing)

아직 기능 구현 전이라 구체적인 케이스는 각 기능 구현 시점에 채운다. 예상되는 우선순위:

1. **타임라인 합성 계산** — 클립 목록(순서, in/out 트림 지점) → 실제 재생/내보내기에 쓰일 구간 배열로 변환하는 순수 함수.
2. **자막 타이밍 검증** — 자막의 시작/종료 시점이 타임라인 길이를 벗어나지 않는지, 서로 겹치는 자막을 어떻게 처리하는지.
3. **내보내기 설정 검증** — 화면비/해상도 프리셋 값이 유효 범위인지.
4. **미디어 가져오기 시 지원 포맷 판별** — [지원 미디어 포맷/코덱](media-format-support.md) 기준으로 허용/거부를 판정하는 순수 함수.

## UI 테스트 (`palladiumUITests`, XCTest)

핵심 플로우는 기능 구현 후 정할 예정. 예상 후보:

1. 미디어 가져오기 → 타임라인에 클립 추가 확인
2. 클립 트림 → 결과 반영 확인
3. 여러 클립 이어붙이기 → 순서 변경 확인
4. 내보내기 → 결과 파일 생성 확인

## 컨벤션

- 유닛 테스트는 Xcode가 이미 스캐폴딩한 대로 **Swift Testing**(`import Testing`, `@Test`, `#expect`)을 쓴다. XCTest로 되돌리지 않는다.
- UI 테스트는 템플릿대로 **XCTest** 유지.
- 인메모리 테스트 픽스처(가짜 클립/타임라인 데이터)를 만드는 헬퍼가 필요해지면 `palladiumTests` 내 공용 파일로 두어 테스트마다 중복 작성하지 않는다.

## 다음 단계

이 문서의 원칙(계산 로직을 View 밖으로 분리)은 화면을 만들기 전, 즉 타임라인/클립 모델을 구현하는 시점부터 지켜야 나중에 되돌아가 리팩터링하지 않는다.
